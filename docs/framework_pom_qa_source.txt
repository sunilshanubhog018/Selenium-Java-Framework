Q1. What is Page Object Model (POM) in Selenium?
Page Object Model is a design pattern where each web page in the application has a corresponding Java
class. This class contains the locators (element identifiers) and the methods (actions) for that page. Tests
interact with the page through these methods instead of directly using Selenium commands.
// LoginPage.java
public class LoginPage extends BasePage {
private final By usernameInput = By.name("username");
private final By loginButton = By.cssSelector("input[value='Log In']");
public void login(String user, String pass) {
type(usernameInput, user);
type(passwordInput, pass);
click(loginButton);
}
}
Q2. What is the difference between BasePage and BaseTest?
BasePage is the parent class for all Page Objects. It contains reusable Selenium methods like click(), type(),
getText() that all pages inherit. BaseTest is the parent class for all Test classes. It handles browser setup
(@BeforeMethod) and teardown (@AfterMethod).
■ Banking example: LoginPage extends BasePage (uses click/type methods). LoginTest extends BaseTest
(uses driver, setUp/tearDown).
Q3. Why do we declare locators as 'private final By' in page objects?
private: Only the page class should access its own locators. Tests should call page methods (login()) not
locators directly (By.name('username')). final: Locator values never change after assignment — they are
constants. By type: Stores just the address of the element, not the element itself. This avoids stale element
exceptions.
// Correct approach
private final By usernameInput = By.name("username");
// Wrong approach — finds element immediately, causes StaleElementException
private WebElement usernameInput = driver.findElement(By.name("username"));
Q4. What is ConfigReader and why is it needed?

ConfigReader is a utility class that reads key=value pairs from config.properties file. Without it, you'd
hardcode URLs, browser names, and credentials in Java — meaning a single change requires editing
multiple files. With ConfigReader, you change ONE line in config.properties and the entire framework picks it
up.
// Without ConfigReader — bad practice
driver.get("https://parabank.parasoft.com"); // hardcoded in 50 files!
// With ConfigReader — good practice
driver.get(ConfigReader.get("base.url")); // reads from config
Q5. Explain the static block in ConfigReader.
The static block runs exactly ONCE when the class is first used. It opens config.properties, loads all
key=value pairs into a Properties object in memory, then closes the file. All subsequent calls to
ConfigReader.get() read from memory — no file I/O. This is efficient because the file is read only once
regardless of how many tests call ConfigReader.
static {
try {
FileInputStream file = new FileInputStream("config.properties");
properties = new Properties();
properties.load(file);
file.close();
} catch (IOException e) {
throw new RuntimeException("Config load failed: " + e.getMessage());
}
}
Q6. What is ExcelReader and how does it support data-driven testing?
ExcelReader uses Apache POI to read test data from .xlsx files. In data-driven testing, test scenarios

Q8. Why do we use @BeforeMethod and @AfterMethod in BaseTest?
@BeforeMethod runs BEFORE every @Test method — it opens a fresh browser. @AfterMethod runs
AFTER every @Test method — it closes the browser. This ensures test isolation: each test gets a clean
browser with no cookies or session from previous tests. If test 1 logs in, test 2 starts fresh and won't be
affected.
■ Banking example: If Test 1 logs in as admin and Test 2 tests invalid login, without @BeforeMethod they'd
share the same browser — Test 2 would already be logged in, causing a false pass.
Q9. What is the difference between implicit wait and explicit wait?
Implicit wait: Applied globally to ALL findElement calls. The driver waits up to N seconds for any element
before throwing NoSuchElementException. Set once in setUp(). Explicit wait: Applied to SPECIFIC
conditions. WebDriverWait waits for a particular condition (visible, clickable) on a particular element for N
seconds. More precise than implicit wait.
// Implicit wait — applies to ALL elements
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
// Explicit wait — applies to SPECIFIC element + condition
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(15));
wait.until(ExpectedConditions.elementToBeClickable(loginButton)).click();
Q10. How does the @DataProvider annotation work in TestNG?
@DataProvider is a method that returns Object[][] (2D array). Each inner array represents one test run's
parameters. TestNG automatically calls the @Test method once for each row, passing the row values as
method parameters. The test count in reports equals the number of rows.
// Returns 3 rows → test runs 3 times
@DataProvider(name = "users")
public Object[][] getData() {
return new Object[][]{
{"admin", "admin123", "pass"},
{"wronguser", "wrongpass", "fail"},
{"", "", "fail"}
};
}
Q11. What is method chaining in Page Objects and why is it useful?
Method chaining is when each action method returns 'this' (the page object itself), allowing multiple method
calls in a single statement. It makes test code more readable and concise.
// With method chaining (returns this)
loginPage.enterUsername("user")
.enterPassword("pass")
.clickLogin();
// Without method chaining (verbose)
loginPage.enterUsername("user");
loginPage.enterPassword("pass");

Q12. Why should Page Objects NOT contain assertions?
Page Objects should only perform actions and return data — never assert. Assertions belong in test classes.
Reason: if login() had Assert.assertTrue(success) inside it, you couldn't reuse login() for negative tests where
failure is expected. Keeping assertions out of pages makes them reusable for both positive and negative
scenarios.
// WRONG — assertion in page object
public void login(String user, String pass) {
type(usernameInput, user);
clickLogin();
Assert.assertTrue(isLoggedIn()); // Should NOT be here!
}
// CORRECT — assertion in test class only
@Test
public void testLogin() {
loginPage.login("user", "pass");
Assert.assertTrue(loginPage.isLoggedIn()); // Correct place
}

Q2. How do you handle a flaky test environment like a shared public test server?
This is a real problem in banking projects. Our approach: 1. Database initialization: @BeforeSuite hits the
admin API to reset the database before the suite runs 2. Dynamic test data: Each test registers a unique user
(username + System.currentTimeMillis()) to avoid conflicts with other teams 3. Retry mechanism: Configure
rerunFailingTestsCount in Maven Surefire plugin 4. Environment-specific config: Separate config files for
DEV/QA/UAT so tests point to isolated environments 5. Health check: Before suite, verify the environment is
up with a simple HTTP check
@BeforeSuite
public void initializeDatabase() {
// Reset ParaBank DB before ALL tests run
driver.get(adminUrl);
driver.findElement(By.cssSelector("button[value='INIT']")).click();
}
// Dynamic username prevents duplicate conflicts
String username = "test_" + System.currentTimeMillis();
Q3. Explain how you implemented data-driven testing for login scenarios in your banking
framework.
We used Apache POI + TestNG @DataProvider. The Excel file has columns: TestCaseID, Category,
Description, Username, Password, Expected, Execute. The Execute column acts as a run flag — setting it to
'No' skips that test case without deleting it. Special values in Username: CONFIG_USERNAME reads from
config.properties, REGISTER_NEW registers a fresh user. This handles both credential types in one Excel
file. Categories covered: Positive E2E (login → transfer → verify), Negative Empty Fields, Invalid Credentials,
Special Characters, Boundary values.

Q4. How does your screenshot listener work? How do you get the driver from the listener?
TestListener implements ITestListener. In onTestFailure(), we get the test class instance via
result.getInstance(), cast it to BaseTest, and call getDriver() to get the WebDriver. We then cast driver to
TakesScreenshot and capture the screenshot as a FILE. The filename includes the test method name and
timestamp for uniqueness.
@Override
public void onTestFailure(ITestResult result) {
Object testInstance = result.getInstance();
WebDriver driver = ((BaseTest) testInstance).getDriver();
TakesScreenshot ts = (TakesScreenshot) driver;
File src = ts.getScreenshotAs(OutputType.FILE);
String timestamp = new SimpleDateFormat("yyyyMMdd_HHmmss").format(new Date());
String path = "test-output/screenshots/" + result.getMethod().getMethodName()
+ "_" + timestamp + ".png";
Files.copy(src.toPath(), Paths.get(path));
}
■ In banking test automation, screenshot evidence is required for audit trails. RBI and banking regulators
require proof that regression tests were executed — screenshots serve as compliance documentation.
Q5. What is the difference between having two @BeforeMethod methods — one in BaseTest
and one in LoginTest?
BaseTest @BeforeMethod (setUp): Runs FIRST. Handles browser setup — reads browser from config,
creates driver, sets timeouts. Same for ALL test classes. LoginTest @BeforeMethod (navigateToLoginPage):
Runs SECOND (TestNG guarantees parent first). Handles page-specific setup — navigates to the login URL,
creates the LoginPage object. This separation means BaseTest stays generic (works for any website) while
each test class handles its own navigation (AccountsTest navigates differently than LoginTest).

Q6. How would you make the framework support parallel execution?
For thread-safe parallel execution: 1. Replace protected WebDriver driver with ThreadLocal 2. Use
driver.set() in setUp() and driver.get() for access 3. Each thread gets its own driver instance — no shared
state 4. Thread-specific download directories (already done with Thread.currentThread().getId()) 5. Configure
testng.xml with parallel='methods' and thread-count 6. Ensure page objects receive driver via constructor
(already done — no static driver)
// Thread-safe driver
private static ThreadLocal driver = new ThreadLocal<>();
public static WebDriver getDriver() { return driver.get(); }
@BeforeMethod
public void setUp() {
driver.set(new ChromeDriver(options));
}
@AfterMethod
public void tearDown() {
if (driver.get() != null) {
driver.get().quit();
driver.remove(); // Important — prevents memory leak
}
}
Q7. Behavioral: Describe a situation where a test was passing but the feature was actually
broken.
In our ParaBank framework, the testValidLogin test was passing even when we entered 'wronguser' and
'wrongpass'. The database was corrupted and accepting any credentials. Root cause: The test only checked
URL.contains('overview') — it didn't verify the logged-in user's name or account data. Lesson: Assertions
must be meaningful. Checking URL alone is insufficient — we added verification of account data visible on
the overview page to confirm we're in the right account. In real banking projects, we also cross-verify login
against the database to ensure the correct user's data is shown.
■ This is a common interview scenario — tests that pass for the wrong reasons. In banking, a false pass on
login could mean security is broken.
Q8. Behavioral: How did you handle the unstable ParaBank public environment in your
framework?
The public ParaBank instance is shared by thousands of people worldwide, causing database corruption. We
handled this in 3 ways: 1. @BeforeSuite database initialization: Automatically hits the admin page and clicks
Initialize before any test runs 2. Dynamic usernames with timestamps: 'user_' + System.currentTimeMillis()
ensures no duplicate conflicts 3. Removed impossible-to-pass tests: We removed negative credential tests
from the Excel file when the environment accepts any credentials — these are environment defects, not
automation defects In real banking projects, we'd use a dedicated isolated QA environment with a fresh
database snapshot before each run.
