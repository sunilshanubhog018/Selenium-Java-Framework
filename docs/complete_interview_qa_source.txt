SECTION 1: SELENIUM WITH JAVA
Technical Questions - Basic to Advanced
Q1. What is Selenium WebDriver and how does it work?
Answer: Selenium WebDriver is a web automation framework that allows you to control web browsers
programmatically. It works by sending commands to a browser through a browser-specific driver (ChromeDriver,
GeckoDriver, etc.). The WebDriver uses the W3C WebDriver protocol (formerly JSON Wire Protocol) to communicate
with browsers. When you write driver.findElement(By.id("username")), the command is sent to the browser driver,
which then instructs the browser to locate that element. WebDriver supports multiple languages including Java,
Python, C#, and JavaScript.
■ Tip: Mention the W3C protocol upgrade from JSON Wire Protocol to show you understand the evolution.
Q2. Explain the difference between driver.close() and driver.quit()
Answer: driver.close() closes only the current browser window/tab that WebDriver is controlling. If you have multiple
windows open, only the focused one closes. driver.quit() closes ALL browser windows/tabs that were opened by that
WebDriver session and ends the WebDriver session completely, releasing all resources. In practice, you should always
use driver.quit() in your @AfterTest or @AfterClass methods to ensure clean resource cleanup.
■ Tip: Give a practical example - 'If I open 3 tabs in my test, close() closes 1, quit() closes all 3.'
Q3. What are the different types of waits in Selenium? Which one do you prefer and why?
Answer: There are three types: (1) Implicit Wait: Sets a global timeout for all findElement operations. Applied once
per session. Example: driver.manage().timeouts().implicitlyWait(10, TimeUnit.SECONDS). (2) Explicit Wait: Waits for
a specific condition on a specific element. More precise. Example: WebDriverWait wait = new WebDriverWait(driver,
10); wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("element"))). (3) Fluent Wait: Like explicit wait but
with polling interval and exceptions to ignore. I prefer Explicit Wait because it's more precise, only waits when needed,
and gives better control over specific conditions. Implicit wait is too broad and can slow down negative test cases.
■ Tip: Say which you prefer and WHY. Shows decision-making ability.
Q4. How do you handle dynamic elements in Selenium?
Answer: Dynamic elements have IDs or attributes that change on each page load. I handle them using: (1) Relative
XPath: Instead of absolute paths, use attributes that are stable like //div[@class='user-name'][contains(text(),'John')].
(2) Explicit Waits: Wait for elements to be present/visible/clickable. (3) CSS Selectors with attributes: Use partial
attribute matching like [id^='user-'] for elements where ID starts with 'user-'. (4) Index-based selection as last resort:
(//div[@class='item'])[1]. (5) Use ancestor/parent/sibling relationships in XPath to locate elements relative to stable
elements.
■ Tip: Give a real example from your framework - 'In my framework, I handle dynamic IDs using...'.
Q5. Explain Page Object Model (POM). Why is it important?
Answer: Page Object Model is a design pattern where each web page is represented as a Java class. The class
contains WebElements (locators) and methods to interact with those elements. Benefits: (1) Separation of concerns:
Test logic is separate from page locators. (2) Maintainability: If UI changes, you only update the page class, not all
tests. (3) Reusability: Methods can be reused across multiple tests. (4) Readability: Tests read like plain English -
loginPage.enterCredentials(user, pass); loginPage.clickLogin(). In my framework, I have a BasePage class with
common methods (click, type, waitFor), and specific page classes like LoginPage, HomePage that extend BasePage.

Q6. How do you handle alerts, pop-ups, and confirmation boxes in Selenium?
Answer: I use the Alert interface in Selenium. First, I switch to the alert: Alert alert = driver.switchTo().alert(). Then: (1)
For simple alerts: alert.accept() to click OK. (2) For confirmation boxes: alert.accept() for OK, alert.dismiss() for Cancel.
(3) For prompt boxes: alert.sendKeys("text") to enter text, then accept(). (4) To get alert text: String text =
alert.getText(). Important: Always add an explicit wait before switching to alert to ensure it's present, or you'll get
NoAlertPresentException.
■ Tip: Mention exception handling - 'I wrap alert handling in try-catch for NoAlertPresentException'.
Q7. How do you handle frames and iframes?
Answer: Frames are HTML documents within HTML documents. To interact with elements inside a frame, I must first
switch to it using: (1) By index: driver.switchTo().frame(0) - not recommended as order can change. (2) By name or
ID: driver.switchTo().frame("frameName") - best if frame has name/id. (3) By WebElement: WebElement
frameElement = driver.findElement(By.id("frameId")); driver.switchTo().frame(frameElement) - most reliable. After
interaction, I switch back: driver.switchTo().defaultContent() to return to main page, or driver.switchTo().parentFrame()
to go one level up. In my framework, I have a switchToFrame() utility method in BasePage.
■ Tip: Mention nested frames - 'For nested frames, I switch sequentially: frame1 -> frame2'.
Q8. What is the difference between findElement() and findElements()?
Answer: (1) findElement(By locator): Returns a single WebElement. If multiple elements match, it returns the first
one. If no elements match, it throws NoSuchElementException. (2) findElements(By locator): Returns a List. If
multiple elements match, it returns all. If no elements match, it returns an empty list (NOT an exception). Use case:
findElements() is useful when you want to check if an element exists without exception handling:
if(driver.findElements(By.id("optional")).size() > 0) { //element exists }. Also use it when dealing with multiple similar
elements like rows in a table.
■ Tip: Give practical example - 'I use findElements() to get all product items on a page'.

Selenium - Intermediate Level Questions
Q9. How do you handle multiple windows/tabs in Selenium?
Answer: Every window has a unique window handle (string ID). Process: (1) Get main window handle: String
mainWindow = driver.getWindowHandle(). (2) Perform action that opens new window (click link with target="_blank").
(3) Get all window handles: Set allWindows = driver.getWindowHandles(). (4) Iterate and switch: for(String window :
allWindows) { if(!window.equals(mainWindow)) { driver.switchTo().window(window); /* work on new window */
driver.close(); /* close when done */ } }. (5) Switch back: driver.switchTo().window(mainWindow). In my framework, I
have a switchToNewWindow() utility method that handles this.
■ Tip: Mention that you ALWAYS switch back to main window and close child windows to avoid memory leaks.
Q10. What is the difference between XPath and CSS Selector? Which is faster?
Answer: XPath: Can traverse both forward and backward (parent, sibling, ancestor). Can use text content:
//button[text()='Login']. More powerful but slightly slower. CSS Selector: Can only traverse forward (child, descendant).
Cannot use text content. Faster than XPath. Syntax is cleaner for IDs and classes. My preference: CSS for simple
locators (ID, class, attributes) because it's faster. XPath when I need parent traversal or text matching. Performance
difference is negligible for small test suites, but matters for large suites (1000+ tests).
■ Tip: Say 'In my 80-test API framework, I mix both based on what's more maintainable'.
Q11. How do you perform drag and drop operations?
Answer: I use the Actions class: Actions actions = new Actions(driver); WebElement source =
driver.findElement(By.id("draggable")); WebElement target = driver.findElement(By.id("droppable"));
actions.dragAndDrop(source, target).perform(). Alternative approach for more control:
actions.clickAndHold(source).moveToElement(target).release().perform(). Note: perform() is essential - it actually
executes the action. In my framework, I have an actionsDragAndDrop() method in BasePage that includes explicit
waits before performing the action.
■ Tip: Mention that you add waits before drag-drop: 'I wait for elements to be visible and enabled'.
Q12. How do you take screenshots in Selenium? When do you take them?
Answer: I use TakesScreenshot interface: TakesScreenshot ts = (TakesScreenshot)driver; File source =
ts.getScreenshotAs(OutputType.FILE); FileUtils.copyFile(source, new File("./screenshots/test.png")). In my framework,
I take screenshots: (1) On test failure (in @AfterMethod with ITestResult to check status). (2) Before and after critical
actions for debugging. (3) For visual comparison in some cases. I store them with timestamp and test name:
screenshot_loginTest_20250130_143022.png. Screenshots are attached to Extent Reports automatically.
■ Tip: Mention WHERE you store screenshots and HOW you attach to reports.

Factory for driver initialization. I use TestNG for test execution, Maven for dependency management.

Q14. How do you handle HTTPS certificate errors in Selenium?
Answer: I use browser-specific capabilities: For Chrome: ChromeOptions options = new ChromeOptions();
options.setAcceptInsecureCerts(true); WebDriver driver = new ChromeDriver(options). For Firefox: FirefoxOptions
options = new FirefoxOptions(); options.setAcceptInsecureCerts(true). Alternatively, for Chrome:
options.addArguments("--ignore-certificate-errors"). This is useful for testing environments with self-signed SSL
certificates. In production, proper certificates should be used, but for dev/test environments, this approach works.
■ Tip: Mention security - 'I only use this in non-prod environments for testing purposes'.
Q15. What is StaleElementReferenceException and how do you handle it?
Answer: This exception occurs when an element you've located is no longer attached to the DOM - maybe the page
refreshed, or element was removed/re-rendered. Solutions: (1) Re-locate the element: Don't store WebElement in a
variable for long. Locate it fresh when needed. (2) Use try-catch and retry: Catch the exception and re-find the
element. (3) Use ExpectedConditions: Wait for element to be clickable/visible before interacting. In my framework,
my Page Object methods always locate elements fresh using @FindBy with PageFactory, which reduces this issue.
■ Tip: Give real example - 'I faced this in a dynamic dashboard where elements refreshed via AJAX'.

Q16. How do you handle flaky tests in your framework?
Answer: Flaky tests fail intermittently. My approaches: (1) Proper waits: Use explicit waits instead of Thread.sleep().
(2) Retry mechanism: Implement IRetryAnalyzer in TestNG to retry failed tests: public class RetryAnalyzer
implements IRetryAnalyzer { int counter = 0; int retryLimit = 2; public boolean retry(ITestResult result) { if(counter <
retryLimit) { counter++; return true; } return false; } }. (3) Stable locators: Use IDs/names over XPath when possible.
(4) Synchronization: Wait for page load, AJAX calls to complete. (5) Test isolation: Each test independent, no
shared state. (6) Run tests multiple times in CI/CD to identify flaky ones.
■ Tip: Mention specific retry count - 'I set retry limit to 2, so tests run max 3 times'.
Q17. How do you integrate your Selenium tests with TestNG?

using groups = {"smoke", "regression"} in @Test. (3) Data providers: For data-driven testing: @DataProvider provides
test data to @Test methods. (4) Parallel execution: testng.xml configured with parallel="tests" thread-count="3". (5)
Dependencies: Use dependsOnMethods for tests that must run in sequence. (6) Listeners: Implemented
ITestListener for logging, screenshot on failure, reports.
■ Tip: Show your testng.xml structure if asked - 'I have separate suites for smoke and regression'.

SECTION 2: PLAYWRIGHT WITH JAVA
Technical Questions - Playwright with Java
Q21. What is Playwright and how is it different from Selenium?
Answer: Playwright is a modern browser automation framework by Microsoft that supports Java, Python, JavaScript,
and .NET. Key differences from Selenium: (1) Auto-waiting: Playwright automatically waits for elements to be
actionable (visible, enabled, stable). No need for explicit waits in most cases. (2) Multi-browser support: Single API
for Chromium, Firefox, WebKit (Safari) built-in. (3) Faster execution: Direct browser protocol (CDP for Chrome), no
WebDriver intermediary. (4) Better debugging: Built-in trace viewer, video recording, screenshots. (5) Modern
features: Network interception, geolocation, mobile emulation out-of-the-box. (6) Reliable locators: Better handling of
shadow DOM, iframes. (7) Same language: Since I use Java for both Selenium and Playwright, the transition is easier
- just different API syntax. Playwright is better for modern web apps with SPAs and dynamic content.
■ Tip: Emphasize that you can use the same Java knowledge for both Selenium and Playwright.
Q22. Explain Playwright's auto-waiting mechanism.
Answer: Playwright performs automatic actionability checks before every action. When I write page.click("#button") in
Java, Playwright automatically: (1) Waits for element to be attached to DOM. (2) Waits for element to be visible. (3)
Waits for element to be stable (not moving/animating). (4) Waits for element to be enabled (not disabled attribute). (5)
Scrolls element into view if needed. This happens automatically with default timeout of 30 seconds. I can change
timeout: page.click("#button", new Page.ClickOptions().setTimeout(5000)). This eliminates most flaky tests caused by
timing issues. I only use explicit waits for non-standard conditions like waiting for API response:
page.waitForResponse() or custom conditions: page.waitForCondition().
■ Tip: Contrast with Selenium - 'Unlike Selenium where I need WebDriverWait and ExpectedConditions, Playwright
handles this automatically'.
Q23. How do you handle multiple pages/tabs in Playwright?
Answer: Playwright has better multi-page handling than Selenium with Java: (1) Listen for new pages: Page
newPage = context.waitForPage(() -> { page.click("a[target='_blank']"); }). This captures the new page as it opens. (2)
Get all pages: List allPages = context.pages(). (3) Switch to specific page: allPages.get(1).bringToFront(). Unlike
Selenium's window handles (strings), Playwright gives you direct Page objects. Each Page has its own methods like
page.navigate(), page.click(), etc. No need to switch contexts back and forth. In my framework, I have a helper method:
public Page openNewPage() that returns the new Page instance. Much cleaner than Selenium's approach with window
handles.
■ Tip: Emphasize type safety - 'Direct Page objects in Java are type-safe vs Selenium's string window handles'.
Q24. How do you perform API testing within Playwright UI tests?
Answer: Playwright for Java has built-in API testing capabilities: (1) Create API context: APIRequestContext
apiContext = playwright.request().newContext(). (2) Make requests: APIResponse response =
apiContext.get("https://api.example.com/users"); String data = response.text(); or JsonObject json = new
Gson().fromJson(response.text(), JsonObject.class). (3) Share authentication: After UI login, I can save browser
context: context.storageState(new BrowserContext.StorageStateOptions().setPath(Paths.get("auth.json"))), then reuse
in API calls. (4) Hybrid testing: I use API to set up test data (create user via API), then test UI (login with that user),
then verify via API. This makes tests faster - UI for testing user flows, API for setup/verification. Much more efficient
than pure UI automation.
■ Tip: Give example - 'I create test users via API POST, test login via UI, verify user profile via API GET'.

Q25. Explain Playwright's locator strategies in Java. What are the best practices?
Answer: Playwright recommends user-facing locators in Java: (1) Role-based (best):
page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Submit")) - finds by ARIA role. (2)
Text-based: page.getByText("Welcome") - finds by visible text. (3) Label-based: page.getByLabel("Email") - finds
input by associated label. (4) Placeholder: page.getByPlaceholder("Enter email"). (5) Test ID (recommended for
stable tests): page.getByTestId("submit-button") requires data-testid attribute in HTML. (6) CSS/XPath (last resort):
page.locator("#id") or page.locator("xpath=//div"). Best practice: Prefer role and text locators as they test accessibility
and are more resilient to UI changes. I add data-testid attributes in collaboration with developers for critical elements
that need stable locators.
■ Tip: Show you understand accessibility - 'Role-based locators also verify ARIA compliance for screen readers'.
Q26. How do you handle network interception in Playwright with Java?
Answer: Playwright can intercept and modify network requests in Java: (1) Listen to requests:
page.onRequest(request -> System.out.println(request.url())). (2) Block requests: page.route("**/*.{png,jpg}", route ->
route.abort()) - blocks all images for faster tests. (3) Mock API responses: page.route("**/api/users", route ->
route.fulfill(new Route.FulfillOptions().setStatus(200).setBody("{"users":[]}"))). (4) Modify requests:
page.route("**/api/**", route -> { Map headers = new HashMap<>(route.request().headers());
headers.put("Authorization", "Bearer token"); route.continue_(new Route.ContinueOptions().setHeaders(headers)); }). I
use mocking for: (a) Testing error scenarios without breaking backend. (b) Testing without backend dependency. (c)
Speeding up tests by removing unnecessary API calls or large image downloads.
■ Tip: Give use case - 'I mock payment gateway API responses to test checkout flows without real transactions'.
Q27. What is Playwright's trace viewer and how do you use it in Java?
Answer: Trace viewer is a GUI tool for debugging test failures. Setup in Java: (1) Start tracing:
context.tracing().start(new Tracing.StartOptions().setScreenshots(true).setSnapshots(true).setSources(true)). (2) Stop
and save: context.tracing().stop(new Tracing.StopOptions().setPath(Paths.get("trace.zip"))). (3) View traces: mvn
exec:java -e -D exec.mainClass=com.microsoft.playwright.CLI -D exec.args="show-trace trace.zip" or use command:
playwright show-trace trace.zip. Features: (a) Timeline of all actions. (b) Screenshots before/after each action. (c)
Console logs and network calls. (d) DOM snapshots at any point. (e) Source code with exact line that failed. I configure
tracing in my framework to capture on test failure only (saves space). Download trace artifact from GitHub Actions,
analyze locally to debug flaky tests. It's like a DVR recording of your test execution.
■ Tip: Show you use it for debugging - 'Trace viewer helped me identify a timing issue in async form submission'.
Q28. How do you perform parallel execution in Playwright with Java?
Answer: Playwright for Java supports parallel execution through JUnit or TestNG: (1) With JUnit 5: Add
junit-platform.properties with: junit.jupiter.execution.parallel.enabled=true and
junit.jupiter.execution.parallel.mode.default=concurrent. Annotate test class with
@Execution(ExecutionMode.CONCURRENT). (2) With TestNG: Configure testng.xml with parallel="methods"
thread-count="4". (3) Maven Surefire: Configure maven-surefire-plugin with methods and 4. (4) Browser contexts:
Each thread gets its own BrowserContext, ensuring test isolation. Use ThreadLocal if needed. (5) CI/CD sharding: In
GitHub Actions, use matrix strategy to split tests across multiple runners. In my framework: Locally: 3-4 threads. CI/CD:
5-8 threads. My 50 tests run in 4 minutes instead of 15 minutes sequential. Each test is isolated with its own context.
■ Tip: Mention test isolation - 'Each thread has isolated BrowserContext, no shared state between parallel tests'.

SECTION 3: API AUTOMATION (REST ASSURED)
Technical Questions - REST API Testing
Q29. What is REST API and what are the main HTTP methods?
Answer: REST (Representational State Transfer) is an architectural style for web services. RESTful APIs use HTTP
methods: (1) GET: Retrieve data, no body, idempotent. (2) POST: Create new resource, has body, not idempotent. (3)
PUT: Update entire resource, has body, idempotent. (4) PATCH: Update partial resource, has body, idempotent. (5)
DELETE: Remove resource, no body, idempotent. Status codes: 200 OK, 201 Created, 204 No Content, 400 Bad
Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Internal Server Error. In my automation, I test all
CRUD operations - Create(POST), Read(GET), Update(PUT/PATCH), Delete(DELETE) for each endpoint.
■ Tip: Mention REST principles if asked - stateless, client-server, cacheable, etc.
Q30. How do you set up Rest Assured in your project?
Answer: (1) Add dependencies in pom.xml: io.rest-assured:rest-assured, org.testng:testng,
com.fasterxml.jackson.core:jackson-databind for POJO. (2) Import static methods: import static
io.restassured.RestAssured.*; import static org.hamcrest.Matchers.*;. (3) Set base URI: RestAssured.baseURI =
"https://api.example.com". (4) Basic test structure: given() - setup (headers, auth, body), when() - action
(get/post/put/delete), then() - validation (status code, response body). I organize this in my framework with: BaseAPI
class sets base URI and common headers, specific API classes (UserAPI, ProductAPI) extend BaseAPI and contain
endpoint methods.
■ Tip: Mention you use static imports for clean code - 'Makes tests readable like BDD'.
Q31. How do you validate JSON responses in Rest Assured?
Answer: Multiple approaches: (1) Using Hamcrest matchers: .then().body("name", equalTo("John")); .body("age",
greaterThan(18)); .body("users.size()", is(5)). (2) JsonPath: String jsonString = response.asString(); JsonPath jp =
new JsonPath(jsonString); String name = jp.getString("data[0].name"). (3) POJO deserialization: User user =
response.as(User.class); Assert.assertEquals(user.getName(), "John"). (4) JSON Schema validation:
.then().assertThat().body(matchesJsonSchemaInClasspath("user-schema.json")). I prefer combination: Hamcrest for
quick checks, POJO for complex validations. Schema validation for contract testing.
■ Tip: Give real example - 'For user API, I validate email format using regex in schema'.
Q32. How do you handle authentication in API testing?
Answer: Different auth types I've handled: (1) Basic Auth: given().auth().basic("username", "password"). (2) Bearer
Token: given().header("Authorization", "Bearer " + token). (3) OAuth 2.0: First, call /oauth/token to get access_token,
then use it in subsequent requests. (4) API Key: given().header("X-API-Key", apiKey) or as query param
.queryParam("api_key", key). (5) Session-based: Extract cookies from login response, use in next requests. In my
framework: I have AuthManager class that handles token generation and storage. I call it once in @BeforeSuite, use
token across all tests. Refresh token if expired (check status 401).
■ Tip: Mention security - 'I store tokens in properties file, not hardcoded in tests'.

RequestSpecification reqSpec = new RequestSpecBuilder().setBaseUri("https://api.example.com").setContentType(C

Q34. How do you handle file uploads in Rest Assured?

Q35. How do you perform API chaining in your framework?
Answer: API chaining means using response from one API call as input to another: Example: (1) POST /users (create
user) → Extract user ID from response. (2) GET /users/{id} (fetch user details) → Verify data. (3) PUT /users/{id}
(update user) → Use same ID. (4) DELETE /users/{id} (delete user). Implementation: Response createResponse =
given().body(userPayload).when().post("/users"); String userId = createResponse.jsonPath().getString("id"); Response
getResponse = given().when().get("/users/" + userId); In my framework: I have a test data manager that stores such
IDs in a HashMap for the session, accessible across tests. For dependent tests: @Test(priority=1) creates data,
@Test(priority=2) uses it.

SECTION 5: PERFORMANCE TESTING (JMETER/GATLING)
Technical Questions - Load & Performance Testing
Q43. What is performance testing and what are its types?
Answer: Performance testing evaluates system behavior under various load conditions. Types: (1) Load Testing:
Test with expected user load (e.g., 1000 concurrent users). Verify system meets performance requirements. (2) Stress
Testing: Test beyond normal load to find breaking point. Identify maximum capacity. (3) Spike Testing: Sudden
increase in load (e.g., Black Friday sale). Check if system handles traffic spikes. (4) Soak/Endurance Testing:
Sustained load over long period (hours/days). Find memory leaks, resource exhaustion. (5) Scalability Testing: How
system performs when resources (servers, CPU) are increased. In my testing: I primarily did load and stress testing
using JMeter for web applications.
■ Tip: Give example - 'I simulated Black Friday spike with 5000 users in 2 minutes'.
Q44. Explain JMeter architecture and key components.
Answer: Thread Group: Represents virtual users. Configure: Number of threads (users), Ramp-up period (how fast
users start), Loop count (iterations). Samplers: Generate requests - HTTP Request (GET/POST), JDBC Request
(database), FTP Request. Listeners: Collect and display results - View Results Tree (individual requests), Summary
Report (aggregate stats), Graph Results. Timers: Add delays between requests - Constant Timer, Gaussian Random
Timer (simulate real user behavior). Assertions: Validate responses - Response Assertion (text/code), Duration
Assertion (max time). Config Elements: CSV Data Set (parameterize), HTTP Cookie Manager (session handling).
Pre/Post Processors: Extract data (Regular Expression Extractor for correlation). My test plan: Thread Group →
HTTP Defaults → Samplers → Listeners.
■ Tip: Explain like building blocks - 'Thread Group is container, Samplers are actions'.
Q45. How do you perform correlation in JMeter?
Answer: Correlation extracts dynamic values from one response and uses in subsequent requests. Example: Session
token, CSRF token, transaction ID. Steps: (1) Record script, identify dynamic value (e.g., token="abc123" in response).
(2) Add Regular Expression Extractor post-processor to the request that returns token. Reference Name: authToken.
Regular Expression: token="(.+?)". Template: $1$. Match No: 1. (3) Use extracted value in next request: ${authToken}
in parameters or body. Example scenario: Login returns sessionId, use it in all subsequent API calls. In my scripts: I
correlated session tokens for a banking application where each session had unique ID that must be sent with every
transaction request.
■ Tip: Draw parallel to API automation - 'Similar to API chaining, extract from response'.
Q46. How do you analyze JMeter results?
Answer: Key metrics I analyze: (1) Throughput: Requests per second. Higher is better. Target depends on
application (e.g., 100 req/sec for API). (2) Response Time: Average, 90th percentile, 95th percentile. 90th percentile
means 90% of users experienced this response time or better. (3) Error Rate: Percentage of failed requests. Should
be < 1%. (4) Latency: Time to first byte. Network delay. Summary Report listener shows all these. View Results Tree
for debugging failures. Graph Results for trends. I look for: Response times increasing over time (memory leak?), High
error rate at certain load (bottleneck), Throughput plateauing (reached capacity). Recommendations: If 95th percentile
> SLA, need optimization or more resources.
■ Tip: Show business understanding - 'I compare results against SLA requirements'.

===== PAGE 16 =====
Q47. What is Gatling and how is it different from JMeter?
Answer: Gatling is code-based performance testing tool using Scala DSL. Differences: (1) Approach: JMeter uses
GUI, Gatling uses code (Scala scripts). (2) Performance: Gatling is lighter, can simulate more users with same
resources (async non-blocking architecture). (3) Reports: Gatling generates beautiful HTML reports with charts by
default. (4) CI/CD: Gatling easier to integrate in CI/CD (just code). JMeter needs JMX files. (5) Learning curve: JMeter
easier to start (GUI), Gatling requires Scala knowledge. When I choose: JMeter for quick POC, UI-based users. Gatling
for complex scenarios, API load testing, CI/CD integration. In my framework: I have both - JMeter for web application,
Gatling for microservices load testing.
■ Tip: Don't say one is better, say 'I use right tool for the job'.
Q48. How do you integrate performance tests in CI/CD?
Answer: (1) JMeter in Jenkins: Install Performance Plugin. Add build step: Execute shell → jmeter -n -t test.jmx -l
results.jtl. Post-build action: Performance Report Plugin → parse results.jtl, set thresholds (fail build if error rate > 5%).
(2) Gatling in CI: Maven plugin: mvn gatling:test. Reports generated in target/gatling. (3) When to run: Not on every
commit (takes time). Scheduled nightly builds. On release branches. Manual trigger for major changes. (4)
Thresholds: Define acceptable metrics: Response time < 2 sec, Error rate < 1%, Throughput > 50 req/sec. Fail build if
not met. In my setup: Performance tests run nightly on staging environment, results emailed to team with trend
comparison.
■ Tip: Mention environment - 'I run performance tests on staging, never on production'.
