Q1. What is TestNG parallel execution and why is it needed?
TestNG parallel execution allows multiple test methods to run simultaneously across different threads.
Without parallel execution, tests run one after another (sequential). With parallel execution, multiple tests run
at the same time, reducing total execution time significantly.
Why needed: A suite of 50 tests taking 40 minutes sequentially can complete in 10-15 minutes with 3 parallel
threads.
testng.xml:
This runs 3 tests simultaneously instead of one at a time.
Q2. What is ThreadLocal and why is it used in parallel execution?
ThreadLocal is a Java class that provides thread-local variables. Each thread accessing a ThreadLocal
variable gets its own independent copy. Without ThreadLocal, multiple threads share the same WebDriver
instance, causing tests to interfere with each other.
// WITHOUT ThreadLocal (NOT thread-safe)
protected WebDriver driver; // shared by all threads!
// WITH ThreadLocal (thread-safe)
private static ThreadLocal driver = new ThreadLocal<>();
public static WebDriver getDriver() { return driver.get(); }
// Each thread gets its OWN driver
Q3. What is Extent Reports and what does it generate?
Extent Reports is a reporting library that generates beautiful HTML reports for test execution. It shows
pass/fail/skip counts, test logs, screenshots attached to failed tests, system information, and execution
timeline. The report is a single HTML file that can be shared with managers and stakeholders.
ExtentSparkReporter reporter = new ExtentSparkReporter('report.html');
reporter.config().setTheme(Theme.DARK);
ExtentReports extent = new ExtentReports();
extent.attachReporter(reporter);
ExtentTest test = extent.createTest('testLoginValid');
test.log(Status.PASS, 'Login successful');
extent.flush(); // writes report to disk

Q4. What is the Singleton pattern used in ExtentManager?
Singleton ensures only ONE instance of ExtentReports is created for the entire test suite. All tests write to the
same report. Without Singleton, each test class would create its own report, resulting in multiple incomplete
reports instead of one comprehensive report.
public class ExtentManager {
private static ExtentReports extent;
public static ExtentReports getInstance() {
if (extent == null) { // create only if null
extent = createInstance();
}
return extent; // same instance every time
}
}

Q6. What is headless browser execution and when is it used?
Headless mode runs Chrome without a visible browser window. The browser runs in the background — no
GUI. This is required in CI/CD environments like GitHub Actions because they are Linux servers with no
display. Headless is also faster than visible mode.

@BeforeSuite runs exactly ONCE before all tests in the entire suite. We used it to initialize the ParaBank

Q10. What is driver.remove() and why is it important in parallel execution?
driver.remove() removes the driver reference from ThreadLocal after the test completes. Without it, the
ThreadLocal variable holds a reference to the closed browser session, causing a memory leak. In parallel
execution with many tests, this can crash the JVM with OutOfMemoryError.

===== PAGE 4 =====
@AfterMethod
public void tearDown() {
if (driver.get() != null) {
driver.get().quit(); // closes browser
driver.remove(); // removes from ThreadLocal
wait.remove(); // removes wait too
}
}
Q11. What Chrome arguments are essential for running on Linux CI/CD?
Linux CI servers have no display and limited shared memory. Without specific Chrome arguments, Chrome
crashes immediately. These arguments stabilize Chrome on Linux:
--no-sandbox: Disables Chrome's sandbox (required on Linux)
--disable-dev-shm-usage: Uses /tmp instead of /dev/shm (prevents crashes)
--headless=new: Runs without display
--disable-gpu: Disables GPU hardware acceleration
--remote-debugging-port=0: Avoids port conflicts

chromeOptions.addArguments('--disable-dev-shm-usage');
chromeOptions.addArguments('--headless=new');
chromeOptions.addArguments('--disable-gpu');

Q12. What is extent.flush() and when must it be called?
extent.flush() writes the in-memory report data to the HTML file on disk. Without calling flush(), the HTML file
remains empty or incomplete. It must be called AFTER all tests complete — in the onFinish() method of
TestListener (ITestListener). If flush() is not called, no report is generated even if all tests ran.
@Override
public void onFinish(ITestContext context) {
// Must call flush() here — after ALL tests complete
extent.flush(); // writes ExtentReport.html to disk
// Without this line — report file is empty!
}

Q1. You have 50 tests taking 40 minutes. How would you reduce execution time to 10 minutes?
Implement parallel execution with 4 threads using ThreadLocal WebDriver:
1. Make driver ThreadLocal (private static ThreadLocal)
2. Update testng.xml: parallel='methods' thread-count='4'
3. Ensure all page object methods use getDriver() not shared driver
4. Use dynamic test data (unique usernames per thread) to avoid DB conflicts
5. Remove unnecessary Thread.sleep() — replace with explicit waits
Result: 50 tests / 4 threads = ~12-13 minutes. Further optimization with --headless=new reduces browser
startup time too.

BaseTest.java:

// Each test uses its own isolated driver instance
Q2. Walk through how Extent Reports integrates with your TestNG framework.
Integration works through ITestListener interface:
1. ExtentManager creates ONE ExtentReports instance (Singleton)
2. TestListener implements ITestListener
3. onTestStart() creates a new ExtentTest node for each test
4. We store ExtentTest in ThreadLocal (parallel-safe)
5. onTestSuccess/Failure/Skip updates the node status
6. onTestFailure captures screenshot and attaches to report
7. onFinish calls extent.flush() to write HTML file
Key insight: ExtentTest (individual test node) uses ThreadLocal, but ExtentReports (the report itself) is
shared — this is intentional. All threads write to ONE report but each writes to their OWN node.
// ThreadLocal for parallel-safe test nodes
private static ThreadLocal extentTest = new ThreadLocal<>();
// Shared report (Singleton)
private static ExtentReports extent = ExtentManager.getInstance();
onTestStart() → extentTest.set(extent.createTest(name));
onTestSuccess() → extentTest.get().log(Status.PASS, msg);
onTestFailure() → extentTest.get().log(Status.FAIL, msg);
onFinish() → extent.flush();
Q3. How do you handle unstable test environments like ParaBank public instance?

===== PAGE 6 =====
ParaBank's public instance is shared globally — other users corrupt the database. Our strategies:
1. @BeforeSuite DB initialization: Hits admin.htm and clicks Initialize before any test runs
2. Dynamic usernames: 'user_' + System.currentTimeMillis() ensures unique users per run

4. Graceful handling: Remove Assert from registration — don't crash the test if DB is temporarily unhealthy
5. Skip known-bad tests: Mark negative credential tests as known-fail when DB accepts any credentials
In production: Use isolated QA environment with DB snapshot reset before each CI run.

Q5. What is the difference between parallel='methods' and parallel='classes' in testng.xml?

===== PAGE 7 =====
parallel='methods': Each individual @Test method runs in its own thread. Maximum parallelism — 3 threads
run 3 different test methods simultaneously, even from different classes.
parallel='classes': Each test CLASS runs in its own thread. All methods within a class run sequentially on the
same thread.
For our banking framework, we use parallel='methods' because:
- Each test is independent (registers fresh user)
- No shared state between tests
- Maximum speed improvement
Use parallel='classes' when tests within a class have dependencies (login once, then run multiple tests).
# methods: 3 individual tests run at same time
→ testValidLogin (thread 1)
→ testValidRegistration (thread 2)
→ testTransfer (thread 3)
# classes: 3 test classes run at same time
→ All LoginTest methods (thread 1)
→ All RegisterTest methods (thread 2)
→ All AccountsTest methods (thread 3)
Q6. How does your framework handle test failures — screenshot capture to report attachment?
Complete failure handling chain:
1. Test fails → TestNG calls onTestFailure(ITestResult result)
2. TestListener.captureScreenshot() called
3. Get driver: BaseTest.getDriver() (static ThreadLocal — thread-safe)
4. Cast to TakesScreenshot → screenshot as FILE
5. Save to: test-output/screenshots/testName_timestamp.png (absolute path)
6. Return absolute path to onTestFailure
7. MediaEntityBuilder.createScreenCaptureFromPath(path) attaches screenshot to ExtentTest node
8. Report shows: test name + failure reason + screenshot embedded in HTML
Absolute paths are critical — relative paths break when report is opened outside project folder.
private String captureScreenshot(ITestResult result) {
WebDriver driver = BaseTest.getDriver(); // thread-safe
TakesScreenshot ts = (TakesScreenshot) driver;
File src = ts.getScreenshotAs(OutputType.FILE);
String path = System.getProperty('user.dir')
+ '/test-output/screenshots/'
+ testName + '_' + timestamp + '.png';
Files.copy(src.toPath(), Paths.get(path));
return path; // absolute path for report
}
Q7. Behavioral: Describe a challenge you faced with CI/CD and how you fixed it.

===== PAGE 8 =====
Challenge: Chrome crashed on first test startup on GitHub Actions — showing 'Chrome instance exited' error.
All 52 tests were skipped because the very first @BeforeMethod failed.
Root cause: GitHub Actions Linux runner had insufficient memory for Chrome's default startup.
Fix applied:
1. Added --disable-gpu argument (Chrome was trying to use GPU on headless Linux)
2. Added --remote-debugging-port=0 (avoided port conflicts)
3. Added --disable-extensions (reduced startup overhead)
4. Added rerunFailingTestsCount=1 in Maven Surefire (auto-retry first failure)
Lesson: CI environments need extra Chrome stability flags that aren't needed on local Windows machines.
Always test your framework on Linux headless before assuming it will work on CI.
Q8. Behavioral: How did you ensure your 52-test suite was maintainable and scalable?
Three key design decisions for maintainability:
1. POM separation: Locators and actions in page objects, assertions in test classes. If ParaBank changes a
button's ID, I update ONE locator in ONE page object — not 20 test methods.
2. ConfigReader: All environment-specific values (URL, browser, timeouts) in one config.properties file.
Switching from QA to UAT environment = change ONE property.
3. Dynamic test data: 'user_' + System.currentTimeMillis() ensures no test depends on pre-existing data.
Tests are self-contained — can run in any order, any environment.
For scaling: Adding a new test = create page object method + add @Test. Framework scales to 500 tests
without changing architecture.
